# 15. 网站图片管理技术文档

> 本文档基于 `/var/www/B2B` 项目真实代码编写，描述「网站图片管理」功能的实现方式、数据结构与数据流。
> 目标：让运营人员可以在 Strapi 后台直接更换网站公共图片（首页 Banner、页头背景、Logo、分享图等），无需改动 HTML / CSS / JS。

---

## 1. 功能定位

网站图片分为两套系统，互不干扰：

| 系统 | 内容类型 | 用途 |
| --- | --- | --- |
| 设备图片 | `api::equipment.equipment` 的 `images` / 图集 | 设备产品图片，由 Equipment 管理 |
| 网站公共图片 | `api::website-image.website-image`（本文档） | 网站其他位置的图片：首页 Banner、页头背景、Logo、OG 分享图、Favicon 等 |

运营人员进入 **Strapi 后台 → 内容 → 网站图片** 即可：查看、搜索、按页面/位置/分类/状态筛选、预览、更换、上传、修改 ALT / 说明、启用/禁用、排序。

更换图片后，**重新运行 `npm run build-pages`**，网站对应位置即自动使用新图片。

---

## 2. 数据结构（Content-Type）

文件：`backend/src/api/website-image/content-types/website-image/schema.json`

- kind：`collectionType`
- collectionName：`website_images`
- displayName：网站图片
- draftAndPublish：**关闭**（图片配置即时生效，无需发布流程）

字段：

| 字段 | 类型 | 说明 | 后台显示名 |
| --- | --- | --- | --- |
| `name` | string（必填） | 运营识别名称，如「首页 Banner 1」 | 图片名称 |
| `key` | string（必填，唯一，正则 `^[a-z0-9]+(?:_[a-z0-9]+)*$`） | 系统定位编号，前端按它取图 | 标识 key（禁止修改） |
| `page` | enumeration | global / home / catalog / solutions / support / about / faq / contact | 所属页面 |
| `position` | enumeration | hero_banner / page_header / solutions_area / sidebar / product_area / header / footer / social_share / favicon / other | 使用位置 |
| `category` | enumeration（可空） | banner / product / solution / about / support / common / other | 图片分类 |
| `image` | media（单图，images） | Strapi 媒体库图片 | 图片 |
| `alt` | string | 无障碍 / SEO 替代文字 | 替代文字 ALT |
| `caption` | text | 图片说明（可空） | 图片说明 |
| `description` | text | 后台备注（用途、建议尺寸） | 用途说明 |
| `enabled` | boolean（默认 true） | 是否启用；禁用后页面保持原样 | 启用 |
| `sort_order` | integer（默认 0） | 排序，越小越靠前 | 排序 |

`key` 是唯一标识，禁止运营修改；前端页面通过 `data-wb-img="<key>"` 引用。

公开权限：在 `backend/src/index.js` 的 `bootstrap` 中，已为 public 角色授予 `api::website-image.website-image.find` 与 `findOne`，供 `build-pages.js` 读取全量配置。

## 3. 图片槽位注册表（Website Image Mapping）

文件：`scripts/website-image-slots.js`（站点根目录）

本文件是「网站图片」的**唯一槽位定义**，由两处共用：

1. `backend/scripts/migrate-website-images.js` —— 初始化 / 修复 Strapi 中的 Website Image 条目
2. `scripts/build-pages.js` —— 读取 Strapi 数据并写入静态页面 / CSS

槽位来源：对 `index.html`、`about.html`、`solutions.html`、`support.html`、`faq.html`、`equipment-catalog.html` 及 `assets/*.css` 的实际扫描结果，**不凭空创建**。

每个槽位字段：

| 字段 | 说明 |
| --- | --- |
| `key` | 机器唯一标识，前端 `data-wb-img="key"` 引用 |
| `name` | 后台显示名称 |
| `page` / `position` / `category` | 后台筛选维度 |
| `sort_order` | 排序 |
| `enabled` | 是否启用 |
| `alt` / `caption` / `description` | 默认 ALT / 说明 / 后台帮助 |
| `mode` | 注入方式（见第 4 节） |
| `defaultFile` | 初始化时登记到媒体库的现有文件（相对 `assets/images/equipment/`） |
| `cssOverlay` | 配置图片后叠加的渐变遮罩（保证叠字可读） |

## 4. 前端注入方式（mode）

`build-pages.js` 按 `mode` 决定如何把图片写进前端：

| mode | 作用 | 实现 |
| --- | --- | --- |
| `inline-bg` | 替换元素行内 `style` 的 `background-image` | `replaceImgMarkers()` 正则替换（如首页 3 张 Banner） |
| `meta` | 替换 `<meta>` 的 `content`（OG / Twitter 分享图） | `replaceImgMarkers()`（如 `default_og_image`） |
| `css` | 由生成的 `assets/website-images.css` 设置 `background-image` | `writeWebsiteImageCss()`（如页头背景、Logo、方案配图） |
| `link` | 生成 `<link rel="icon">`（Favicon） | `replaceOptionalBlock()`（如 `site_favicon`） |

`replaceImgMarkers()` 只处理**本身带 `data-wb-img` 属性**的标签，且对所有替换做了**幂等**处理：重复构建结果一致，标记属性不会被消耗掉。

取不到数据 / 图片缺失 / 槽位禁用时，页面**保持原有外观**，不会出现裂图。

## 5. 前端数据流

```
Strapi 后台「网站图片」
        │  运营更换图片并保存
        ▼
Strapi API  /api/website-images  (public 可读)
        │  build-pages.js → fetchWebsiteImages()
        ▼
Website Image 配置  { key: { path, alt, caption, enabled } }
        │
        ├── processStaticPages()  → 替换 index/about/solutions/support/faq/equipment-catalog 中带 data-wb-img 的标记
        │       · <img src> / <meta content> / <link href> / 行内 background-image
        │
        └── writeWebsiteImageCss() → 生成 assets/website-images.css（css 模式槽位）
```

图片路径解析：
- `mediaToPath(row.image)` 把 Strapi 媒体 URL（`/uploads/<name>`）转换为站点相对路径 `assets/images/equipment/<name>`（设备页与根页面沿用此约定）。
- `assets/website-images.css` 位于 `assets/` 目录内，因此其中的背景图统一使用**站点绝对路径** `/uploads/<name>`（`toUploadsUrl()` 转换），避免相对 `assets/` 目录解析出错。
- nginx 已配置 `location /uploads/ { alias /var/www/B2B/assets/images/equipment/; }`，所以 `/uploads/<name>` 与 `assets/images/equipment/<name>` 指向同一物理文件。

## 6. 媒体库登记（初始化脚本）

文件：`backend/scripts/migrate-website-images.js`

作用（幂等，可重复执行）：
1. 把站点现有公共图片（首页 3 张 Banner、Mining Solutions.jpg）**复制**为新文件名并登记进 Strapi 媒体库（`plugin::upload.file`）。原始文件一律保留，绝不删除或覆盖。
2. 依据 `scripts/website-image-slots.js` 写入 13 个 Website Image 条目；已存在（按 `key`）的条目只做文本补全，不覆盖运营人员已更换的图片。

运行：
```bash
cd /var/www/B2B/backend
node scripts/migrate-website-images.js
```

安全约定：
- 不删除任何现有文件
- 不修改任何 Equipment 数据
- 已存在且已配置图片的槽位保持原样

> 注意：脚本会临时启动一个独立的 Strapi 实例（`createStrapi().load()`）来读写数据库，结束时 `strapi.destroy()` 可能与运行中的主实例争用连接池，偶尔在退出阶段打印 `KnexTimeoutError`——**不影响已提交的数据**，可忽略。

## 8. 静态页面生成脚本改动

文件：`scripts/build-pages.js`（原有设备页生成逻辑不变，新增网站图片段落）

新增函数：
- `fetchWebsiteImages()`：读取 `/api/website-images`，返回 `{ key: { path, alt, caption, enabled } }`；取不到时不抛错，返回空对象并告警（避免 Strapi 未升级时整站构建失败）。
- `replaceImgMarkers(html, images)`：替换带 `data-wb-img` 标记的 `<meta>` / `<link>` / `<img>` / 行内背景图。
- `writeWebsiteImageCss(images)`：生成 `assets/website-images.css`，仅对启用且配置了图片的 css 模式槽位输出规则。
- `processStaticPages(images)`：处理 6 个静态页面（只替换图片来源，不改布局/CSS/动画/响应式）。
- `toUploadsUrl(p)`：把图片路径转成 `/uploads/<name>` 绝对形式，供 CSS 使用。
- `defaultOgImagePath()`：供设备页 OG 回退使用。

`main()` 流程：先 `fetchWebsiteImages()`，再生成设备页，最后 `writeWebsiteImageCss()` + `processStaticPages()`。

`STATIC_PAGE_TARGETS`：`index.html`、`about.html`、`solutions.html`、`support.html`、`faq.html`、`equipment-catalog.html`。

## 13. 列表页后台优化（v1.2.1）

### 13.1 问题诊断

首版后台 `layouts.list` 写成 `[{name, size, ...}]` 对象数组（编辑页语法）。Strapi 5 Content Manager 列表布局只接受字段 UID 字符串数组。校验失败被忽略 → Strapi 退回默认 `["id","name","key","page"]` 4 列 → 运营看到「空白列表」。

### 13.2 修复方案

`scripts/configure-website-image-admin.js` 中 `layouts.list` 改为字符串数组：`["image","name","page","position","category","enabled","sort_order","key"]`。

| 顺序 | 字段 UID | 中文列名 | 含义 |
| --- | --- | --- | --- |
| 1 | image | 图片 | 缩略图，原生点击预览 |
| 2 | name | 图片名称 | 运营看的（不是 key） |
| 3 | page | 所属页面 | 枚举 |
| 4 | position | 使用位置 | 枚举 |
| 5 | category | 图片分类 | 枚举 |
| 6 | enabled | 状态 | 启用 / 禁用 |
| 7 | sort_order | 排序 | 可拖动 |
| 8 | key | 标识 | 系统唯一标识（辅助） |

搜索：`name` / `key`。筛选：`page` / `position` / `category` / `enabled`。

### 13.3 中文 Tag 与 Badge：Strapi 5 的限制与应对

**约束**：

1. Strapi 5.52.3 Content Manager 列表单元格渲染不读取 `enumNames`，显示原始枚举值。
2. 规范 §二 禁止修改 `node_modules` / Strapi Core。
3. 生产模式 `start` 不重编译 admin bundle（仅 `develop` 会热加载 `src/admin/extensions/`）。
4. Strapi 5 枚举值规则 `^[_A-Za-z][_0-9A-Za-z]*$`，不允许中文 enum value。

**通过三层补偿达成「运营一眼看清」**：

1. **搜索/筛选下拉**：使用 `enumNames`（Strapi 原生支持中文）。
2. **编辑表单**：枚举字段渲染中文 `enumNames`。
3. **列表列标题**：覆盖 `metadatas[*].label` 为中文。

如果未来升级到支持 enumNames cell 的 Strapi 版本，Schema 已用 enumNames，可零迁移升级。

### 13.4 实施涉及文件

```

scripts/website-image-slots.js                                            (枚举值与 schema 一致)

backend/scripts/translate-website-image-enums.js + rollback                (数据迁移工具)
docs/15-网站图片管理技术文档.md                                            (本文档)
docs/16-网站图片运营操作手册.md                                            (更新)
```

### 13.5 数据迁移策略

数据迁移严格遵循规范 §二十六：

1. 迁移前：源码备份 + 数据库导出 `/tmp/wi_backup.csv`。
2. 迁移实施：用 `translate-website-image-enums.js`（SQL 直写 + 字典映射），数据列严格保留英文 value，中文放在 `enumNames`。
3. 验证：`layouts.list` 已写入；API 返回 13 行；3 个启用槽位有真实图片；启用状态下前台页面有图可访问。

### 13.6 已知限制（v1.2.1）

1. **列表枚举单元格不显示中文**。当前已通过三层补偿（筛选中文 / 编辑表单 / 列名）。
2. **预览大图**：Strapi 5.52.3 原生 Media Library 弹窗。
3. **快速更换图片**：操作列中点击「编辑」打开完整编辑页，使用原生 Media Library 弹窗选图。
4. **快速筛选 Tag**：Strapi 5.52.3 在列表上方未暴露快速 Tab，使用右上「筛选」下拉。

## 14. Strapi Media → 前端数据闭环（v1.3.0）

### 14.1 根因

13 个 Website Image 槽位中**有 9 个 `enabled: false`**（`home_solutions`、`about_side`、5 个 `page_header`、`site_logo`、`favicon`）。
`build-pages.js → writeWebsiteImageCss()` 只为 `enabled=true` 的 CSS 槽位生成规则——结果：

- 11 个 `enabled=false` 的 CSS 槽位 → `assets/website-images.css` 是空
- 运营在后台改图 → 数据库更新但 CSS 未生成 → 前端完全不变

这是用户感知「前端没生效」的真因。后台 → API → build-pages.js → HTML 的链路其实早已打通。

### 14.2 修复（最小改动）

```diff
# scripts/website-image-slots.js
- { key: 'home_solutions', ..., enabled: false, ... }
+ { key: 'home_solutions', ..., enabled: true, defaultFile: 'Mining Solutions.jpg', ... }
```

- 启用 9 个 CSS 槽位
- 复用 `assets/images/equipment/Mining Solutions.jpg` 作为默认图（**仅登记元数据，不复制文件**）
- 5 个 `page_header` 槽位补回 `mode: 'css'` + `cssOverlay: OVERLAY_HERO`

`site_logo` 和 `favicon` 仍 `enabled=false`（基础设施槽位，无默认图时启用会破坏外观，保持禁用待运营挑图后启用）。

### 14.3 迁移脚本（幂等）

`backend/scripts/migrate-website-images.js` 重写"已存在条目"的判定：只**补缺**（cur.image 为空时填 defaultFile），不动运营已配置的图。
新增"text-字段冲突"判定——若 slots 字段与 DB 不一致，更新文本字段但不覆盖 image。

### 14.4 端到端验证

```
BEFORE  hero-1 URL = 1788670622_899fd2_...jpg  (file_id=36)
SWAP    UPDATE website_images_morph SET file_id=37 WHERE ...
BUILD   node scripts/build-pages.js  → 62 pages 0 fail
AFTER   hero-1 URL = 1788670622_e2fbce_...jpg  (file_id=37)  ✅
ROLLBACK UPDATE morph back to file_id=36
BUILD   0 fail
FINAL   hero-1 URL = 1788670622_899fd2_...jpg  ✅
```

证据：home_hero_1 内联 url 真从 899fd2 切到 e2fbce，再回到 899fd2。

### 14.5 现在 CSS 输出

`assets/website-images.css` 含 7 条规则（含 `!important` 覆盖原页面 CSS）：

```css
[data-wb-img="home_solutions"] { background-image: url("/uploads/...") !important; }
[data-wb-img="about_side"]     { background-image: url("/uploads/...") !important; }
```
